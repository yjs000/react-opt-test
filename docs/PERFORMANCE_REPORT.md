## 4. CSR 최적화 후 탐색 캡처

2026-11-23 Chrome DevTools Performance 캡처 1건. 주소는 `localhost:5173`, 캡처 시점의 검색어는 `t`, 선택된 정렬은 제목순이다. 빌드 모드, 캐시 상태, 정렬 전환 순서와 정렬 캐시 적중 여부는 캡처에서 확인할 수 없다.

| Performance Summary 항목 | CSR 기본 탐색 기록 | CSR 최적화 후 탐색 기록 |
| ------------------------ | -----------------: | ---------------------: |
| 선택 범위                | 15 ms–6.77 s       | 0 ms–19.47 s           |
| Scripting                | 629 ms             | 5,928 ms               |
| Rendering                | 285 ms             | 3,102 ms               |
| Painting                 | 105 ms             | 350 ms                 |

**개선율은 산출할 수 없다.** 위 수치는 각 선택 구간 전체의 누적값이다. 기존 기록은 정렬을 추가하기 전이고 새 캡처는 선택 범위가 약 2.9배 길다. 새 구간에는 React Developer Tools(607.0 ms)와 Wappalyzer(114.0 ms)의 메인 스레드 활동도 표시된다. Frames 트랙에는 2,500 ms, 1,950 ms, 1,900 ms 구간이 보이지만, 개별 정렬 조작을 선택한 상태가 아니므로 정렬 반영 시간이나 React 커밋 시간으로 해석할 수 없다.

현재 코드는 정렬 캐시가 적중해도 필터에 남은 카드 전체를 목록에 전달한다. 캡처에는 스크립트와 브라우저 렌더링 비용이 모두 보이지만, 어느 쪽이 정렬 체감 지연을 주도하는지는 개별 상호작용의 Main 트랙을 확인해야 한다.

정렬 개선율은 정렬 기능이 있는 기준 버전과 최적화 버전을 프로덕션 빌드에서 비교한다. 확장 프로그램을 끄고 같은 화면 크기, 데이터, 검색어, 캐시 조건을 사용한다. 두 버전에서 `제목순 → 평점순 → 제목순`의 마지막 조작부터 목록의 새 순서가 화면에 표시될 때까지 최소 3회 측정해 중앙값을 비교한다. 정렬 함수 실행 시간과 브라우저 렌더링 시간도 따로 확인한다.

## 5. 정렬 포함 기준과 CSR 최적화 버전 비교

2026-11-23에 기준 커밋 `23c5295`와 현재 코드 `6b5e4f1` 및 작업 트리의 포스터 `loading="lazy"` 변경을 각각 별도 경로에서 프로덕션 빌드했다. 두 버전 모두 동일한 JSON 7,956개를 사용한다. 초기 검색어 `t`는 7,697개, `th`는 2,622개와 일치했다.

Chrome 157.0.8103.80, 1280 × 800 CSS 픽셀, 배율 1, 확장 프로그램 비활성화, HTTP 캐시 비활성화, 로컬 서버 조건에서 측정했다. 별도 Chrome 창으로 시작했으나 페이지가 백그라운드로 전환돼 프레임 콜백이 멈췄다. 최종 수치는 헤드리스 Chrome에서 얻었다. 포스터 요청을 양쪽 모두 차단해 로컬 목록 처리 비용을 비교했다. 포스터 로딩, LCP, 실제 사용자 INP 및 이미지 lazy loading의 효과는 이 실험의 측정 범위 밖이다.

각 회차는 새로 탐색한 뒤 `기본순 → 제목순 → 평점순 → 제목순 → 기본순`을 수행하고, 검색어를 `t → th`로 바꿨다. 초기 로딩은 탐색 시작부터, 정렬과 필터는 브라우저에서 이벤트를 발생시킨 시점부터 측정했다. 예상한 목록 개수와 첫 8개 제목이 DOM에 반영됐는지 확인하고 그 다음 `requestAnimationFrame`에서 시간을 읽었다. 화면 반영 시점의 근사치이며 React Profiler의 렌더 시간과는 측정 범위가 다르다.

버전 실행 순서를 회차마다 번갈아 바꿨다. 양쪽 예열 1회와 끝까지 완료되지 않은 마지막 회차를 제외하고 완료된 3쌍의 중앙값을 사용했다.

| --- | ---: | ---: | ---: |
| 초기 로딩 → 첫 목록 반영 | 2,743.4 ms | 2,735.7 ms | 7.7 ms 감소 (0.3%) |

제목순 복귀에서 가장 큰 단축을 관찰했다. 이 전환은 최적화 코드상 제목순 배열을 재사용하는 경로지만, 두 빌드에는 카드 memo와 다른 변경도 함께 있으므로 349.3 ms 전체를 정렬 캐시 개선분으로 볼 수 없다. 첫 회차를 제외한 제목순 복귀의 개별값은 기준 1,975.4–2,532.8 ms, 최적화 1,860.1–2,002.0 ms였다. 최적화 후에도 7,697개 카드의 순서 변경에서 약 2초가 남았다. 초기 로딩 차이 7.7 ms는 반복 간 변동 범위 안이었다.

단일 검색의 결과 표시는 설정된 디바운스 300 ms에 가까운 295.3 ms만큼 늦어졌다. 이 측정은 검색 결과가 표시되는 시점을 본다. 입력창 반응 시간과 연속 입력에서 생략된 목록 갱신 횟수는 별도로 측정하지 않았다.

## 6. 별도 Chrome 창에서 초기 로딩·정렬·`tiger` 연속 입력 재측정

2026-11-23. 기준은 정렬 기능이 있는 `23c5295`, 최적화는 `6b5e4f1`과 작업 트리의 포스터 `loading="lazy"` 변경이다. 두 빌드의 JSON은 SHA-256이 동일하다. 이 7,956개 데이터는 TMDB 검색어 `t`의 스냅샷이고, 앱 실행 중에는 번들에 포함된 JSON을 Promise로 반환한다. 앱의 로컬 제목 필터를 거친 초기 화면은 7,697개다. 검색 비교에서는 초기 `t`를 그대로 두고 약 100 ms 간격으로 `iger`를 입력했다. 입력 단계별 결과는 `ti` 6,828개, `tig` 603개, `tige` 422개, `tiger` 420개였다.

별도 Chrome 157.0.8103.80 창, 1280 × 800 CSS 픽셀, DPR 1, 확장 프로그램 비활성화, 포스터 요청 차단, Vite 프로덕션 번들에서 측정했다. Cold는 HTTP 캐시를 비활성화한 새 문서, warm은 JS·CSS가 디스크 캐시에 있는 새 문서다. 정렬은 warm 초기 목록에서 기본순 → 제목순 → 평점순 → 제목순 → 기본순을 수행했다. 각 정렬 후 첫 8개 제목을 검증했다. 로딩·정렬·검색 결과는 DOM이 반영되고 두 번째 `requestAnimationFrame`이 호출된 시점까지의 시간이다. 입력 반응은 브라우저가 `input` 이벤트를 처리하기 시작한 시점부터 두 번째 프레임 콜백까지이며, 물리 키 입력에서 이벤트 시작까지의 대기 시간과 실제 픽셀 표시 시점은 측정 범위 밖이다. 입력으로 텍스트를 삽입했으므로 실제 사용자 INP로 해석할 수 없다.

카드 `memo` 제거, 300 ms 디바운스 제거, 포스터 lazy 속성 제거 빌드를 각각 임시 복사본에서 만들었다. 각각 현재 빌드에서 해당 변경만 제거했다. 프로덕션 빌드에는 React Profiler 계측을 추가하지 않았다.

첫 회차는 예열로 제외했다. 완료된 5쌍에서 회차마다 버전 실행 순서를 뒤집었고, 표에는 버전별 중앙값, 두 중앙값의 차이, 회차별 차이의 중앙값(짝 비교)을 함께 표시했다. 회차별 측정값이 크게 달라 100 ms 기준은 같은 회차의 짝 비교도 확인했다.

### 초기 로딩 체감을 설명하기 위해 확인할 질문

1. **무엇이 먼저 보였나?** 제목과 카드 틀, 첫 포스터, 입력 가능 시점 중 어느 항목이 빨랐는가? 이번 실험은 전체 목록 DOM 뒤의 프레임을 봤다. 초기 7,697개 카드 중 6,773개에 포스터 경로가 있다. 체감이 포스터에 있었다면 현재 코드에서 lazy만 켜고 끈 뒤, 실제 포스터를 허용한 cold/warm 각각에서 LCP 요소, 첫 포스터 표시 시점, 초기 전송량을 측정한다. 화면 밖 이미지 요청을 미루면 상단 리소스의 대역폭 경쟁이 줄 수 있다. 첫 화면의 포스터까지 lazy를 걸면 그 이미지의 요청이 늦어질 수도 있다. [web.dev 이미지 지연 로딩](https://web.dev/learn/performance/lazy-load-images-and-iframe-elements)
2. **첫 화면에 7,697개를 한 번에 그릴 필요가 있나?** 두 빌드 모두 약 1.54 MB의 JS에 영화 JSON을 포함하고 처음에 7,697개 카드를 만든다. 초기 트레이스에서 JS 파싱·평가, React 커밋, 스타일 계산·레이아웃·페인트를 확인한다. 전체 데이터에서 검색·정렬한 뒤 화면에는 20개만 표시하는 비교를 하면, 계산량을 유지하면서 DOM 규모가 지연에 미치는 영향을 확인할 수 있다.
3. **정렬은 비교 함수와 DOM 이동 중 어디가 더 무거운가?** 제목순 배열을 재사용해도 카드 순서는 바뀐다. 정렬 함수 실행 시간과 DOM 재배치·레이아웃 시간을 따로 계측하고, 정렬 캐시만 제거한 빌드와 첫 선택·복귀를 각각 비교한다.
4. **입력 반응성을 유지하면서 결과 대기를 줄일 수 있나?** 같은 tiger 입력 속도에서 150 ms와 300 ms, 디바운스 없음, 목록 컴포넌트의 입력을 지연하는 useDeferredValue를 각각 비교한다. 가장 느린 글자, 마지막 글자 뒤 결과 지연, 실제 중간 목록 갱신 횟수를 함께 기록한다. [React useDeferredValue](https://react.dev/reference/react/useDeferredValue)

## 7. 포스터 lazy 로딩과 150 ms 디바운스 후속 실험

2026-11-23. 앞서 관찰한 401.2 ms는 같은 회차의 최종 결과 표시 시간 차이의 중앙값이다. 300 ms 타이머는 일부만 설명한다. 디바운스가 없으면 최종 글자 전에 목록이 422개까지 줄어 마지막 갱신에서는 2개만 제거한다. 디바운스가 중간 갱신을 합치면 최종 갱신이 시작될 때 7,697개가 남아 최대 7,277개를 한 번에 제거한다. 타이머 실행 지연, React의 목록 갱신과 DOM 변경, 다음 프레임 처리 비용이 함께 더해질 것으로 예상했다.

### 디바운스 시간과 최종 목록 처리

Chrome 157 별도 창, 1280 × 800, 포스터 차단, 프로덕션 번들에서 약 100 ms 간격으로 초기 t에 iger를 입력했다. 설정별 5회, 회차마다 실행 순서를 순환했다. 150 ms와 300 ms 임시 빌드에서 최종 검색어의 타이머 콜백 시작과 제목 필터 함수를 계측했다. DOM 관찰 시점과 두 번째 프레임 콜백의 차이에는 브라우저 작업, 프레임 스케줄링과 계측 비용이 함께 포함된다. 구간별 중앙값의 합은 전체 중앙값과 다를 수 있다.

| 지표 | 디바운스 없음 | 150 ms | 300 ms |
| --- | ---: | ---: | ---: |
| 회차별 가장 느린 글자 | 362.4 ms | 103.0 ms | 61.0 ms |
| 마지막 글자 → 최종 목록 프레임 | 21.2 ms | 373.7 ms | 537.8 ms |

| 최종 DOM 관찰 → 프레임 콜백 | 17.1 ms | 51.0 ms | 50.2 ms |
| 최종 제목 필터 함수 | — | 1.4 ms | 2.0 ms |

관찰된 결과 개수 변화는 디바운스 없음에서 6828 → 603 → 422 → 420, 150 ms에서 420, 300 ms에서 420였다. 150 ms 설정의 마지막 글자 뒤 대기는 300 ms보다 짝 비교 중앙값 157.9 ms 짧았다. 가장 느린 글자의 짝 차이(300 ms 시간 − 150 ms 시간)는 -41.8 ms였다. 제목 필터 자체는 계측한 모든 회차에서 3.0 ms 이내였다. 타이머 이후 시간이 React 계산, DOM 제거, 레이아웃에 각각 얼마나 쓰였는지는 트레이스로 추가 확인해야 한다.

150 ms 빌드의 마지막 글자부터 타이머 실행까지의 범위는 158.5–454.8 ms였다. 설정한 지연은 브라우저가 콜백을 큐에서 실행하기까지의 상한이 아니다.

### 포스터 lazy 로딩 켜기와 끄기

현재 코드에서 포스터의 loading 속성만 바꾼 두 빌드를 비교했다. 데이터의 포스터 URL은 각각 구분하고, 동일한 TMDB JPEG 126,268바이트를 로컬 서버에서 반환했다. Chrome에서 40 ms 지연, 다운로드 10 Mbps, 업로드 5 Mbps를 적용했다. 별도 창에서 설정당 cold/warm 3쌍을 번갈아 실행했다. Cold는 HTTP 캐시 삭제 직후, warm은 동일 URL에 다시 탐색해 JS와 CSS의 디스크 캐시 적중을 확인한 조건이다. 요청 수와 완료 전송량은 탐색 뒤 약 8초까지의 CDP 브라우저 이벤트를 합산했다. 완료 전송량은 완료된 응답의 전송 바이트로, 진행 중 전송은 포함하지 않는다.

| 캐시 | lazy | 첫 목록 ms | 입력창 프레임 ms | 첫 화면 포스터 ms | LCP ms | LCP 요소 | 포스터 요청 | 완료 응답 | 완료 전송 MB |
| --- | --- | ---: | ---: | ---: | ---: | --- | ---: | ---: | ---: |
| cold | 끄기 | 2,659.6 | 2,081.4 | 2,808.4 | 1,688.0 | H1 | 6,766 | 49 | 6.20 |
| cold | 켜기 | 2,466.3 | 1,629.8 | 3,181.4 | 1,652.0 | H1 | 16 | 16 | 2.02 |
| warm | 끄기 | 1,246.1 | 203.6 | 1,304.8 | 224.0 | H1 | 6,766 | 120 | 7.34 |
| warm | 켜기 | 996.8 | 129.4 | 1,042.4 | 148.0 | H1 | 16 | 16 | 0.00 |

첫 화면 포스터는 뷰포트와 겹치는 첫 이미지의 load 이벤트 뒤 두 번째 프레임 콜백이고, 입력창 프레임은 검색창이 DOM에 생긴 뒤의 두 번째 콜백이다. 지속적인 입력 가능 시점이나 실제 INP는 측정하지 않았다. LCP는 탐색 후 약 8초까지의 마지막 브라우저 후보를 기록했다. 같은 포스터 파일로 응답한 로컬 실험이므로 실제 TMDB CDN의 이미지 크기 분포, 연결 및 캐시 조건에서 같은 차이가 난다고 볼 수 없다. [web.dev LCP 최적화](https://web.dev/articles/optimize-lcp)

### 페이지네이션 없이 볼 병목

1. 입력마다 MovieBoard가 7,697개 항목의 JSX를 다시 만드는지 React Profiler에서 본다. 필요하면 목록 전체를 별도의 memo 컴포넌트로 두고 기존 sortedMovies 참조를 전달해, 검색어만 변하고 디바운스된 결과는 그대로일 때 목록 순회를 건너뛰는 실험이 가능하다.
